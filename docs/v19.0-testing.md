# GitLab v19 acceptance

## Source decision

Debian Trixie does not package GitLab. The appliance installs GitLab CE
19.3.0 from GitLab's official Debian 13 repository. GitLab supports its Linux
package on Debian 13 from version 18.5 through Debian's expected June 2030 end
of life. The build binds the repository key by SHA-256 and fingerprint, then
APT verifies the signed repository metadata and the selected package digest.

The selected package and evidence are:

- version `19.3.0-ce.0`;
- repository key fingerprint
  `F6403F6544A38863DAA0B6E03F01618A51312F3F`;
- repository key SHA-256
  `003c0ca2fea61767f8c6de7a1c0f49fc88ea3c8db95e3cd1856b32ce9d876e0f`;
- package SHA-256
  `f88f80cd61d6b2beb35aa7207591d4abdfed0e6c2c42e6ed753dd29ea5de076d`.

## README crosswalk

| Contract | Focused acceptance | Required result |
| --- | --- | --- |
| Root firstboot credentials | Submit the rendered sign-in form with `TKL_TEST_APP_PASS`, then query the authenticated user endpoint with the session cookie | The normal web login identifies `root` |
| Project hosting | Create a private project through the authenticated API and read its committed file through GitLab HTTP | The project exists and its marker is rendered from the repository |
| Git and SSH | Register a throwaway root SSH key, push a commit, then clone it into a fresh directory | The pushed marker survives an SSH Git round trip |
| PostgreSQL and repository services | Read the project row with `gitlab-psql` and require PostgreSQL, Redis, Gitaly, Nginx, and Sidekiq status | The project metadata and GitLab service stack are healthy |
| Background jobs | Require the Sidekiq supervisor process | Sidekiq reports a running process |
| Outbound mail | Require the appliance Postfix unit | Postfix is enabled and active; public mail delivery is outside local acceptance |
| Webmin Postfix module | Require the packaged module directory | The appliance-specific mail administration module is installed |
| Supervised updates | Run `gitlab-update --check` | The installed version, signed Trixie candidate, and required-stop policy are reported without mutation |
| Built-in Let's Encrypt integration | Confirm GitLab owns Nginx and require the appliance's GitLab-specific Confconsole plugin | Certificate issuance requires a public DNS name and is not invoked in local acceptance |
| Inherited administration | Cite unchanged SSH, Webmin, and common platform behavior | Core 19 PASS run `20260824t010251z-1634-32241` at source `24c82ee3540ce545422742b0e28ba6b687c53ec2` remains applicable |

The acceptance fixture revokes its token and SSH key and requests project
deletion on exit. GitLab retains revoked-token audit records according to its
normal product behavior.

Puma can remain running until the supervisor timeout and make the build fail.
The smallest future product correction is to stop Puma and confirm it is down
before stopping PostgreSQL, then retain the existing full-stack stop.

The three product loops fixed package auto-reconfiguration before runit,
fresh-install reconfiguration triggered by `EXTERNAL_URL`, and PostgreSQL 17
cleanup through the Rails database wrapper. The repeated Puma cleanup failure
was found after that budget was exhausted, so no fourth product change was
made. The final retained report and checksum manifest are under
`/home/agent/.local/state/turnkey-v19-harness/failures/gitlab/current/`.

The disposable Docker acceptance first proves the normal service stack, then
stops optional observability services and runs one Puma worker to fit the
7.4 GiB development host. Sidekiq remains available through project and SSH
key creation. These test accommodations do not change shipped appliance
defaults.

## Deferred issues

- GitLab upgrades are supervised because required stops occur at minor
  versions x.2, x.5, x.8, and x.11. The helper reports candidates but does not
  choose or install the next stop.
- The local test checks that the product-specific Let's Encrypt integration is
  retained. Public certificate issuance needs an externally resolvable fixture.
- API project deletion can complete asynchronously. The test submits cleanup,
  but does not wait for GitLab's background deletion worker.
- Fresh GitLab 19 databases do not contain the legacy `ci_runners.token` column
  or `web_hook_logs` relation referenced by two best-effort cleanup statements.
  The statements report errors but do not prevent the build from continuing.
- Docker acceptance does not repeat installer, kernel, or hardware checks.
